# Loreviva 文档编写规范

产品文档面向需要理解、制作、实现或采用 Loreviva 的读者。叙述从产品目标和用户场景展开，解释能力之间的关系、取舍及边界，形成完整的产品逻辑。

## 内容组织

产品概述说明定位、价值和体验；需求说明书定义行为、交互与验收；白皮书解释架构与技术约束；接入指南提供可操作流程；实施计划安排依赖与交付。当前状态只维护一份摘要，详细执行结果保存在工程记录中。

每次修改直接整合到负责的章节，移除失效内容。版本讨论、借鉴过程、竞品比较、授权原话、修改往返及内部执行流水保存在对应档案，不追加到当前产品正文。历史原件、必要来源和第三方版权许可保持完整；整理表达不改变来源事实或隐去必须保留的归属。

## 行文与术语

使用中性、具体的产品语言。以“创作者”“玩家”“业务客户”“平台”“系统”等明确主体描述行为，避免“你提出”“我建议”“AI认为”“按你的要求”等对话表达。AI、Agent、Harness 在描述产品能力时保留其准确含义。

标题说明本节内容，段落解释前因后果。避免口号式排比、反复强调、修订标签和过密术语；可比较的字段用表格，操作顺序用步骤，因果关系用完整句子。世界、角色定义、演员实例、发布版本、世界实例、模型连接和 Skill 等术语保持一致。

## 设计与事实

设计能力、已实现功能、实际验证和商业结果分别表述。未验证的能力不写成上线承诺，局部测试不写成整体通过。限制写在影响读者判断或操作的位置，进度集中在状态记录，避免每段重复免责声明。

编辑不得改变规范中的权限、范围、数值、接口、状态机、恢复语义或验收要求。技术内容保留必要细节，团队与投资人阅读入口优先呈现产品逻辑。机器契约保持工程内唯一来源，文案不建立另一套字段定义。

## 中英文与交付

中英文使用同一产品逻辑、能力范围和状态。英文是对应阅读内容，语句自然表达，不逐字保留中文讨论过程。文档更新后检查术语、链接、标题结构、数值与接口标识；涉及行为或技术变更时另行评审。

导出材料标注准确版本与开发阶段。公开交付继续检查来源、许可、私密隔离及双语一致性，内部记录不随正文一并分发。
