# Persistent isolated package import

After local matching, creators can save a package as an isolated draft, continue editing and inspect revisions. Preview still writes no business data. Actual import checks the original archive, current authority, dependencies, assets and model configuration again.

The import record, protected origin lineage, draft, initial revision and original request receipt commit in one transaction. No background import task or new file-body copy is created; only mapped local READY assets are referenced.

## Use and recovery

1. Read a package in Content and resources, complete local matching and verify source permissions.
2. Import it as an isolated draft. The same operator, product, package ID and version reuse the existing import by default. Changed content or configuration conflicts. Explicitly choose an independent copy when new object identities are needed.
3. Keep the original request key. Stopping the wait, network failure, a server error or an unverifiable reply does not prove rollback. Query the original result, or retry the same key with the original input.
4. Open the isolated draft from the receipt. A fresh page or restarted service can recover the currently authorized receipt using the original key alone.

Use `POST /world/v1/admin/content-packages/imports?product_id=...` with operator authority, `Idempotency-Key`, the original `archive` and `options` in the `PackageImportOptions` format. Options contain the original RESOLVE mapping and `expected_preview_sha256`; optional `copy_key` explicitly requests an independent copy. `GET /world/v1/admin/content-packages/imports/{request_key}?product_id=...` reads the original receipt. The sole machine contract defines the fields.

## Isolation and storage

The server generates local object identities using the installation boundary and a random namespace. Preview identities grant no import authority. Protected DRAFT/OBJECT origin records preserve isolation through copy, archive, history restoration and ordinary create/save reuse of known imported objects. Actual publication independently checks these records.

Migration `0009` adds `content_package_imports` and `content_package_import_lineage`; migrations 1–8 remain unchanged. Subsequent backup and restore work must maintain both tables together with drafts, revisions, commands and receipts.

## Current verification and scope

Six named actual MySQL/HTTP/browser targets passed separately. They cover atomic commit, same-package reuse and conflicts, independent copies, original-key replay, a lost commit reply, final cancellation/revocation/source withdrawal, isolation lineage, refused publication and migration retry. The real browser uploads original file bytes directly. After an actual server commit with a corrupted success reply, it retains the original key, recovers the receipt, opens the draft and recovers on a fresh page. Concentrated SDK regressions cover broken success, invalid structure, 500, 502, unverified refusal and verified refusal.

The initial migration failure, the test proxy omitting uploaded file bytes and targeted repairs are retained. These are not described as one entirely green combined run. Partial-object copy, cross-subject reuse, concurrent requests and revocation in another transaction did not receive dedicated dynamic checks; their lock and authority paths received static review. Unchanged P2/Task8 checks were not repeated.

Working contract 1.8.0 has 70 operations and 192 schemas. Product design 3.1.0 and R0 execution 3.0.1 remain separate. Isolation promotion, local publication, export/second-installation round trips, safe document extraction and the Skill sharing workflow remain future work. Whole Task9 and R0 remain incomplete. Real-model quality, human experience, performance, charging and deployment were not accepted in this scope.
